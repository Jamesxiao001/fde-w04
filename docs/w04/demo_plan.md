# Demo 方案

## 链路与选择理由

**选定链路：复购趋势核查。** 用青禾新 CRM 的真实导出数据，查月内复购率（按月）、月末付费会员复购率，以及覆盖期内的首购情况。每个结论都限定在已经纳入的数据范围内。

**对应的会员运营工作**：运营要判断会员复购到底怎么样，再决定是否做召回、召回谁。小林每周拉"60 天没买"的回访名单（客户材料 04），前提就是先弄清复购在下降，以及下降发生在哪里。

**为什么先验证这一条**：

1. **业务目标**：沈总最关心"会员复购率连续四个季度下滑"（W1、W2 访谈），这次也明确要"能跑起来、最好跟会员复购有关、别再给我看 PPT"（客户材料 03）。
2. **数据能支撑**：导入后的库里能按月算复购。2025-09 至 2026-08 的月内复购率，从 16.73% 一路降到 11.80%，2026-07 最低，为 11.37%（run-02）。同期按月购买的会员账户从 3,653 个增加到 5,473 个。这些数值都已用不经过指标库的独立计算核对一致。
3. **客户能当场判断"对不对"**：复购口径从 W2 起一直没有定下来，沈总说的复购率不一定是"同一自然月买两次"。门店老收银系统的数据没有导出，也会直接影响复购判断。把这两点摆到客户面前，最容易得到具体的纠正反馈（V01、V06："demo 的第一作用是让客户说'不对'"）。
4. **现有能力**：运营 Agent 只能在 38 项指标的范围内查数，不能直接输出会员名单。所以本期不演示"回访名单圈人"，演示能实际跑通的复购查数链路。

**在项目中的位置**：上周已签正式合同和 SOW。这次 demo 是正式项目本期的**第一次阶段检查**，不是 POC，也不是验收（V02）。验收仍然按 SOW 约定进行。

## 数据可用性、最小验证与已有证据

**用到的数据**：

| 数据 | 规模 | 来源 |
| --- | --- | --- |
| 订单 | 接受 167,665 条，覆盖 2024-09-01 至 2026-09-01（不含） | 新 CRM 导出 |
| 会员账户 | 119,754 个 | 同上 |
| 会员卡 | 接受 16,349 张，用于月末付费资格判断 | 同上 |
| 门店 | 403 家 | 同上 |

清洗、隔离和对账见 `docs/w04/data_diagnosis.md` 第三节：订单 168,253 = 接受 167,665 + 隔离 252 + 去重 336，两次导入的结果一致。

**已知异常**，覆盖说明已随查询结果一起交给 Agent：

- 门店老收银系统的消费没有导出；
- 已注销会员的 168 条订单，因为资料被清理而隔离；
- 退款大于实付的 84 条订单隔离；
- 员工卡 299 张隔离；
- 2024-09 以前没有订单。

**结果能否追溯**：

- 每次运行都保存了提问、SQL、查询结果、回答和当时的数据集快照，放在 `artifacts/w04/demo_runs/run-0X/<trace_id>/`。
- 指标数值可以追到 `metrics_run.json` 和独立计算。
- 单条订单可以追到原始 CSV 的记录序号（`trace_records.json`）。

**最小验证链路**：

> 业务问题 → 运营 Agent 选指标（月内复购率／付费会员复购率／首购）→ 在导入后的青禾库上执行 SQL → 回答写明口径和覆盖范围 → FDE 用独立计算核对数字 → 客户评价口径和范围

**已有证据**：

| 证据 | 说明 | 运行 |
| --- | --- | --- |
| 数字正确 | 单月复购率 11.80%、12 个月逐月复购率、付费会员复购率 23.33%、覆盖期首购 3,362 个，全部与独立计算一致 | run-01～04、06、07 |
| 口径表达正确 | 能说清"同一自然月""月末资格只算两种卡""账户不等于自然人" | run-01、03 |
| 覆盖限制会被带出 | 老收银未导出、隔离不当 0 | 全部 ok 的运行 |

## 暂不覆盖范围与待验证条件

| 暂不覆盖 | 原因 | 满足什么条件才扩大 |
| --- | --- | --- |
| 季度复购率、跨月合并的复购 | 指标库只有完整自然月口径，季度问题被拒答（run-05） | 和客户确定季度复购的口径（季度内买两次，还是相邻季度回购）后新增指标；或先让 Agent 把季度问题按月展开回答 |
| 含门店老收银系统／老卡的复购、终身首购 | 数据没有导出（老周 MSG-05458、05502） | 老收银系统负责方确认，并补导覆盖期内的门店会员消费 |
| 按门店拆分复购 | "按门店"默认指成交门店还是归属门店，至今未定（W3 遗留）；付费会员月报规定不按门店拆 | 小林或口径负责人确认默认门店角色 |
| 回访名单圈人、排除员工和勿扰 | Agent 只能查数、不能输出名单；系统里没有员工标识（MSG-05500）；CRM 的触达限制备注没有时间 | 产品具备名单输出能力，拿到员工名单，并按"勿扰名单与系统任一边有限制就不联系"的规则实现 |
| 复购下滑的原因分析 | 只能看到现象，看不到原因；新会员增多、老收银缺口都可能拉低比率（推断） | 复购口径定下来，补齐老收银数据后，再按入会批次分组看 |

## 实际运行入口、bad case 与下一步

所有运行都在 `artifacts/w04/demo_runs/`，使用导入后的项目 `.runtime/w04/run-01/project-e`（修订后的指标库）。标注文件是 `artifacts/w04/demo_annotation.json`，导出结果是 `artifacts/w04/demo_run.json`。

| 运行 | 提问 | 结果 | 判定 |
| --- | --- | --- | --- |
| run-01 | 2026年8月的月内复购率是多少？ | 11.80%，口径和覆盖都说明了；范围在句末 | 通过 |
| run-02 | 2025年9月到2026年8月，每个月的月内复购率分别是多少？ | 12 个月全对，限制说明完整 | 通过 |
| run-03 | 2026年8月月末付费会员的复购率是多少？ | 23.33%，资格口径完整 | 通过 |
| run-04 | 2026年8月有多少会员是第一次在青禾购买？ | 3,362 正确；把真实数据称为"测试覆盖期"，先给数字后限定范围 | **bad case**（调优前） |
| run-05 | 2025年7月到2026年6月这四个季度，青禾会员的复购率是不是连续下滑？ | unsupported，一律拒答 | **bad case** |
| run-06 | 同 run-04 | 提示词其实没改：追加规则的命令因 PowerShell 弯引号报错，没有生效，所以等同原样重跑。这次没出现"测试"字样 | 波动证据，保留 |
| run-07 | 同 run-04，追加回答规则后 | 首句先限定"新 CRM 自 2024-09-01 起"，不再出现"测试"，说明不是终身首次；但把整批隔离的 252 笔说成本次未纳入，并且和注销订单重复计算 | **bad case**（调优后仍有问题） |

**bad case 的下一步处理**：

1. **run-04 → run-07（调优）**：
   - 改动位置：提示词／上下文，只改一处，见 `demo_run.json` 中的 `tuning`。
   - 效果：目标问题改善了，但出现了新的越界：把整批 24 个月的隔离数套到了单月结论上。
   - 下一步：不再逐题堆提示词，而是找共同原因。覆盖说明里的隔离数是整批口径，应在 `coverage_notes` 中注明"为 24 个月整批数量，不对应单月"，属于数据／上下文的修改，或者在回答规则里统一要求"批次级隔离数不得套到单个窗口"。改完用 run-01～07 的同一组问题回归，确认原来答对的问题没有变差。
   - run-06 说明问题不是每次都出现，单次对照不能证明效果稳定，第七周用更多问题重复验证。
2. **run-05（拒答）**：
   - 原因：Harness 和指标约束只支持完整自然月，问到季度就直接拒答。
   - 下一步：在 catalog 约束里写明"问季度时按月列出季度内各月，不合并成季度值"，或者修改 Harness 策略，然后用原题重跑。
   - 这一处不和本轮调优同时改，避免一次改两处。
3. **catalog 来源引文**：4 项首购指标仍保留着 W03 来源引文"测试覆盖期"，这是 run-04 出现该说法的来源之一。下一轮评估是否在来源里注明"W03 测试数据阶段的原文"。

## 判断说明：关键假设及继续、缩小范围、调整方向的条件

**关键假设**：

| 编号 | 假设 | 已有证据 | 待验证条件 |
| --- | --- | --- | --- |
| H1 | 运营 Agent 在青禾真实数据上，能把复购相关的数算对，并说清口径 | run-01～04、06、07 的数字全部与独立计算一致 | 客户在 demo 上确认这些口径是他们要的 |
| H2 | "同一自然月买两次"能代表沈总说的"复购率" | 无。W2 起口径就没定，小林说不是她一个人能定的 | 沈总和口径负责人在 demo 上给出判断，这是本次最想得到的"不对" |
| H3 | 月内复购率的下降反映了真实的业务变化，而不是数据覆盖造成的 | 只有现象：比率下降，同期购买账户在增加 | 补导老收银数据后复算；按入会批次分组看新会员稀释的影响 |
| H4 | 回答能把结论限定在覆盖范围内，不把未知当 0，也不一律拒答 | 覆盖说明能带出；run-07 改善了范围前置；run-05 拒答、run-07 越界还没解决 | 共同原因修复后回归 |

**最小验证链路与选择依据**：

- 只验证"查复购"这一段，不验证"出名单"和"召回执行"。
- 依据：数据和现有能力能支撑这一段，见本文第二节；它又直接对应发起人的问题。
- 宁可窄，不能断：从业务问题到可追溯的数字，再到客户评价，整条链完整（V06）。

**演示时按这个顺序进行**：

1. 先讲清楚三件事：要解决的问题是复购下滑；用的数据范围是新 CRM、2024-09 起，老收银没有导出；希望客户做出的决定是确认复购口径、是否推进补数。
2. 现场提 run-02 的问题，展示 12 个月的数字和限制说明，并给出独立核对的结果。
3. 主动展示 run-05、run-07 两个 bad case 和处理办法，不只展示成功的运行。
4. 请沈总评价口径，请小林评价能不能用在回访工作里，请老周确认补数条件。
5. 记录三样东西：客户指出的问题、使用中的迟疑、双方答应的下一步。

**下一步的三种走向，各自的条件**：

| 走向 | 判断条件（看了运行结果和反馈就能判断） |
| --- | --- |
| **继续**：沿复购链路往下做 | 沈总或口径负责人确认"月内复购率"可以作为本期复购口径之一，或者给出了明确的替代口径；数字核对无异议；老周给出老收银数据的负责方和补导时间。满足后：补季度展开、修 run-05 和 run-07，回归后进入下一轮演示 |
| **缩小范围** | 客户认为老收银缺口太大，在补数之前不接受"全会员"结论。这时只对"新 CRM 覆盖的渠道和会员"给结论，例如只看小程序、商城，或者只看 2025 年以后入会的账户，明确写成本期有效范围；"全会员复购"推迟到补数以后 |
| **调整方向** | 客户明确说复购率的定义不是"同期买两次"，例如是"上季度买过、本季度又买"的回购，且现有 38 项指标都算不了，或者运营真正要的是"出名单去召回"而不是查数。这时回到场景选择：新增指标，或改做名单类能力，要先和王经理对照 SOW 范围，走变更流程 |
